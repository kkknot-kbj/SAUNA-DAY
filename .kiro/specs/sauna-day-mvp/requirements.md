# SAUNA DAY MVP — 要件定義

## 概要

サウナを起点に休日の過ごし方を決めるサービスのMVP。
ユーザーは条件からサウナを探し、選んだサウナを中心にサ飯・観光・アクティビティ・温泉・宿泊を含む休日プランを得る。

サウナ検索はDBに対する決定的な処理で行い、AIは選択済みサウナに紐付く正確なDBデータのみを使って休日プランを組み立てる。

## 用語定義

| 用語 | 定義 |
|---|---|
| **必須条件** | 満たさない施設を検索結果から除外する条件（日付・人数・出発地・移動時間・日帰り/宿泊・予算・絶対条件） |
| **希望条件** | 一致数をスコアに加算する条件（自然・サウナタイプ・クールダウン・外気浴・体験） |
| **詳細条件** | 「条件を追加」から展開して初めて表示される条件群 |
| **クールダウン体験** | サウナ後に体を冷やす手段の総称。水風呂に限定しない（川・湖・海・雪・天然水・地下水・樽・プール・水風呂・シャワー・なし） |
| **環境** | 施設の周囲にある自然。「近くにある / 見える」を表す（`sauna_environments`） |
| **休日プラン** | 選択したサウナを中心に、時系列で構成された1日または1泊の予定 |
| **ゲスト** | 未認証状態のユーザー。検索・閲覧は可能 |
| **条件一致率** | 希望条件のうち何件を満たしたかの比（例 9/10） |

---

## 要件1: ホーム（探す）

**ユーザーストーリー:** サウナに行きたいと思ったユーザーとして、会員登録なしにすぐ検索を始めたい。

### 受入基準

1. ホームを開いたとき、システムはメインコピー「次の休日、サウナから決めよう。」を最も目立つ要素として表示すること
2. ホームを開いたとき、システムは会員登録・ログインを要求しないこと
3. ホームを開いたとき、システムは以下を**1問ずつ1画面で**尋ねるフローを提供すること
   1. いつ行く？（日付）
   2. 誰と行く？（同行者タイプ。人数の初期値を自動で決める）
   3. どこから？（出発地）
   4. 日帰り / 宿泊
   5. どこまで行ける？（移動可能時間）
   6. 予算
4. **IMPORTANT:** 1画面に複数の問いを並べないこと。条件が多く見える状態を作らない
5. 日付は「今週末 / 来週末 / 日付を選ぶ」を提示し、カレンダーを開かずに選べること
6. 単一選択のステップでは、選択後に次のステップへ自動で進むこと（タップ数を減らす）
7. 各ステップに「指定せず進む」を用意し、すべての項目が任意であること
8. 各ステップから前のステップへ戻れること
9. 現在位置（何問目か）を控えめに示すこと
10. 全ステップの後に確認画面を出し、以下を満たすこと
    - 入力内容を一覧できる
    - 各項目から該当ステップへ戻って直せる
    - 現在の条件で該当する件数を表示する
    - 人数を微調整できる
11. 未入力の項目があっても検索へ進めること（未入力は制約なしとして扱う）
12. 確認画面から、サウナ条件の選択へ遷移すること
13. ステップの遷移の動きは控えめにし、`prefers-reduced-motion` を尊重すること
14. 直近の閲覧履歴がある場合、システムはそれを控えめに表示すること
15. ホームにAIへの言及を一切表示しないこと

---

## 要件2: 条件設定

**ユーザーストーリー:** 条件を指定したいユーザーとして、大量の選択肢に圧倒されず、必要な条件だけを選びたい。

### 受入基準

1. 条件設定画面は次の3つのまとまりで構成すること
   - **休日の枠**（日付・人数・誰と・出発地・移動時間・日帰り/宿泊・予算）。満たさない施設は除外する
   - **サウナの条件**（自然環境・クールダウン・サウナタイプ・外気浴・体験・プライベート性）
   - **詳細条件**（熱源・設備・利用条件・アクセス、および各カテゴリの詳細寄りの項目）
2. 初期表示では、休日の枠とサウナの条件のみを表示すること
3. 詳細条件は「条件を追加」を操作したときにのみ表示すること
4. **IMPORTANT:** 初期表示で大量の条件を並べないこと

### 必須 / 希望はタグ単位で決める

5. **IMPORTANT:** サウナの条件は、カテゴリ単位ではなく**タグ単位**で必須 / 希望を選べること
   「川に入れるのは必須、薪は希望」のような指定ができること
6. 各タグは3つの状態を持つこと
   | 状態 | 検索での扱い |
   |---|---|
   | 未選択 | 無視する |
   | **希望** | 一致数をスコアに加算する（除外しない） |
   | **必須** | 満たさない施設を結果から除外する |
7. タップで 未選択 → 希望 → 必須 → 未選択 と循環すること
8. 同じタグが希望と必須の両方に入らないこと
9. 3つの状態を色だけで区別しないこと。罫線の太さ・アイコン（チェック / 鍵）を併用し、必須は文字でも示すこと
10. 操作方法（もう一度タップで必須になること）を画面上で伝えること
11. 必須にしているタグを、カテゴリを跨いで一覧できること。そこで希望への変更と解除ができること
12. プライベート性（貸切等）も同じ仕組みで扱うこと。カテゴリごとに必須・希望を固定しないこと

### その他

13. 条件を変更したとき、システムは現在の条件で見つかる件数を提示すること
14. 条件はゲスト状態でも端末側に保持され、画面遷移や再訪で失われないこと
15. 検索結果画面で、必須にしている条件を確認できること
16. 必須にしたタグは条件一致率の分母に含めないこと（全件が満たすため差がつかない）

## 要件3: サウナ条件の語彙

**ユーザーストーリー:** サウナに詳しいユーザーとして、自分がこだわる要素を正確に指定したい。

### 受入基準

1. システムは以下のカテゴリと選択肢を保持すること

   | カテゴリ | 選択肢 |
   |---|---|
   | サウナタイプ | 小屋 / テント / バレル / コンテナ / 露天 |
   | 熱源 | 薪 / 電気 / ガス |
   | サウナ設備 | ロウリュ / セルフロウリュ / オートロウリュ / アウフグース / 窓 / 景色 |
   | 自然環境 | 森 / 山 / 川 / 湖 / 海 / 渓谷 / 絶景 |
   | 外気浴 | 森 / 川沿い / 湖畔 / 海辺 / 山 / 星空 / 絶景 / 屋根あり / 雨天利用可 / リクライニング / インフィニティチェア / ハンモック / 寝転び可能 |
   | 体験 | 川ダイブ / 湖ダイブ / 雪ダイブ / 海に入る / 薪焚き / セルフロウリュ / 焚き火 / 星空外気浴 / 朝サウナ / サンセット / サンライズ |
   | プライベート性 | 完全貸切 / 時間貸切 / 半個室 / 男女共用 / 男女別 / 他グループと共有 / 1組限定 |
   | 利用条件 | 水着必須 / 水着レンタル / 裸OK / タオル / 飲食 / 飲酒 / 子ども / ペット / 撮影 |
   | アクセス | 車 / 電車 / 徒歩 / 送迎 / 駐車場 / 未舗装道路 / 林道 / 冬季アクセス / 4WD推奨 |

2. 各選択肢は英語 snake_case の key で保持し、日本語表示名と対応するアイコンを一元管理すること
3. 選択肢の表示に絵文字を使用しないこと（線画アイコンを使用すること）
4. 新しい選択肢の追加が、語彙定義の1箇所の変更で完結すること

---

## 要件4: クールダウン体験

**ユーザーストーリー:** 川に飛び込みたいユーザーとして、「川が近くにある施設」ではなく「川に入れる施設」を見つけたい。

### 受入基準

1. システムはクールダウンを「水風呂」に限定せず、川 / 湖 / 海 / 雪 / 天然水 / 地下水 / 樽 / プール / 水風呂 / シャワー / なし として管理すること
2. 各クールダウンについて、システムは以下の属性を保持できること
   - 水温
   - 水深
   - 飛び込み可否
   - 天然水か
   - 流れの有無
3. **IMPORTANT:** システムは「川が近くにある」と「川に入れる」を別の情報として保持すること
4. **IMPORTANT:** システムは「海が見える」と「海に入れる」を別の情報として保持すること
5. 「川に入れる」で検索したとき、川が近いだけの施設を結果に含めないこと
6. 環境（近接・眺望）には、敷地内 / 徒歩圏 / 眺めるだけ の区別を保持すること
7. 属性が不明な場合、システムは値を保持せず、表示時に「不明」と示すこと

---

## 要件5: 検索とフィルタ

**ユーザーストーリー:** 条件を指定したユーザーとして、条件に合わない施設が混ざらない結果を得たい。

### 受入基準

1. **IMPORTANT:** サウナ検索をAIに行わせないこと。DBへの問い合わせと決定的な処理で実装すること
2. 必須条件を満たさない施設は、システムは結果から**除外**すること（スコアを下げるのではなく落とす）
3. 移動時間の必須条件について、出発地からの所要時間が上限を超える施設を除外すること
4. 予算の必須条件について、最低料金が上限を超える施設を除外すること
5. 人数の必須条件について、受け入れ可能人数の範囲外となる施設を除外すること
6. 日帰り / 宿泊の指定に適合しない施設を除外すること
7. 絶対条件（貸切等）を満たさない施設を除外すること
8. 希望条件については、システムは一致した件数を数え、除外は行わないこと
9. 事実情報が不明（NULL）な項目については、必須条件による除外の判定を行わず、一致にも数えないこと

---

## 要件6: ランキング

**ユーザーストーリー:** 多数の候補を見るユーザーとして、自分に合う順に並んでいてほしい。

### 受入基準

1. システムは以下の要素を加味して並び順を決定すること
   - 条件一致（希望条件の一致数）
   - 距離
   - 料金
   - 人気
   - ユーザーの過去の選択
2. 初期の重みは condition_match 55% / distance 20% / price 10% / popularity 10% / preference 5% とすること
3. **IMPORTANT:** 重みをコードにハードコードしないこと。デプロイなしで変更できる場所から読むこと
4. スコア計算は総合値だけでなく**各要素の内訳**を返すこと
5. 同スコアの場合の並び順が実行ごとに変わらないこと（決定的であること）
6. ゲスト状態では preference の重みを他要素へ再配分すること

---

## 要件7: 検索結果

**ユーザーストーリー:** 結果を見るユーザーとして、写真と要点だけで候補を絞りたい。

### 受入基準

1. 各施設カードに、システムは以下を表示すること
   - 大きな写真
   - 施設名
   - 主要タグ
   - 条件一致率
   - 出発地点からの所要時間
   - 料金
2. カードの表示例に相当する情報密度とすること

   ```
   ○○ SAUNA
   川 / 薪 / 貸切
   あなたの条件  9 / 10
   東京から1時間40分
   ¥4,800〜
   ```

3. 料金が不明な施設では、金額の代わりに「不明」と表示すること
4. 所要時間が算出できない場合、「不明」と表示すること
5. 写真を最も大きな要素として扱うこと
6. カードを画面いっぱいに敷き詰めず、余白を確保したリスト形式とすること
7. 主要タグは3〜4件までに絞って表示すること

---

## 要件8: ランキング理由の開示

**ユーザーストーリー:** 並び順に疑問を持ったユーザーとして、なぜこの順番なのかを知りたい。

### 受入基準

1. 検索結果に、システムは「なぜこの順番？」を確認する手段を提供すること
2. 操作したとき、システムはスコアの内訳（条件一致 / 距離 / 料金 / 人気 / 過去の選択）を表示すること
3. どの希望条件が一致し、どれが一致しなかったかを示すこと
4. 表示にAIへの言及を含めないこと

---

## 要件9: 条件緩和の提示

**ユーザーストーリー:** 結果が少なかったユーザーとして、どの条件を緩めれば選択肢が増えるか知りたい。

### 受入基準

1. 完全一致の件数が少ない場合、システムは条件を緩和した場合の候補数を提示すること
2. 提示は「あと30分移動できれば、条件一致10/10が3件あります」の形式に相当する具体性を持つこと
3. 緩和の対象は移動時間・予算・必須タグの解除・希望条件の除外のうち、最も件数が増えるものを優先して示すこと
4. 提示を操作したとき、システムは条件を緩和した結果へ遷移すること
5. 結果が0件のとき、システムは緩和提示を必ず表示すること
6. **IMPORTANT:** 必須にしたタグの解除を提案できること。必須は施設を除外するため、絞りすぎの主因になりやすい
7. 必須タグを1つ解除しても候補が増えない場合、システムは「必須をすべて希望に変える」提案を出すこと
8. 必須を希望に変える緩和では、そのタグを希望条件として残すこと（一致率には引き続き反映する）
9. 固定の緩和幅（+30分など）で候補が増えない場合、システムは必要な最小の緩和量を算出して提示すること

---

## 要件10: サウナ詳細

**ユーザーストーリー:** 候補を絞ったユーザーとして、その施設の事実情報を正確に確認したい。

### 受入基準

1. 詳細画面に、システムは以下を表示すること
   写真 / 施設概要 / 料金 / 人数 / 営業時間 / サウナタイプ / 熱源 / 温度 / ロウリュ / クールダウン / 水温 / 外気浴 / 景色 / 貸切情報 / 利用条件 / アクセス / 駐車場
2. **IMPORTANT:** 各項目が不明な場合、システムは「不明」と表示し、推測値を表示しないこと
3. クールダウンについて、種類ごとに水温・水深・飛び込み可否を表示すること
4. 詳細画面に「**このサウナで休日を作る**」ボタンを配置すること
5. 詳細画面から「行きたい」に保存できること
6. 予約が可能な施設では、公式予約ページへの遷移手段を提供すること
7. 写真を画面上部の主役として扱うこと

---

## 要件11: 周辺施設の紐付け

**ユーザーストーリー:** サウナを決めたユーザーとして、その周辺で何ができるかを知りたい。

### 受入基準

1. **IMPORTANT:** サ飯・観光・宿泊の候補は、事前にDBへ登録されたレコードから取得すること。その場でAIに検索させないこと
2. サ飯（飲食店）の紐付けは以下を保持すること
   - 距離 / 移動時間 / ジャンル / 価格 / おすすめタイミング / おすすめ理由
3. 観光・アクティビティ（スポット）の紐付けは以下を保持すること
   - 距離 / 移動時間 / 所要時間 / おすすめ度
4. 宿泊の紐付けは以下を保持すること
   - 距離 / 料金 / おすすめ度 / 宿泊タイプ
5. サウナと各カテゴリの関係は多対多とし、中間テーブルで管理すること
6. 詳細画面での紐付け情報の表示は、サウナ本体の情報より下位の扱いとすること

---

## 要件12: 休日プラン

**ユーザーストーリー:** サウナを決めたユーザーとして、そのサウナを中心にした1日の流れを提案してほしい。

### 受入基準

1. 「このサウナで休日を作る」を操作したとき、システムはDBからサ飯 / 観光 / 温泉 / アクティビティ / 宿泊の候補を取得すること
2. **IMPORTANT:** システムは取得した正確なDBデータのみをAIに渡すこと
3. **IMPORTANT:** AIはDBに存在しない施設名・料金・営業時間・所要時間を生成してはならないこと
4. プランは時系列で表示すること

   ```
   10:00 東京出発
   12:00 ○○ SAUNA
   15:00 ○○食堂
   16:30 ○○湖
   18:00 ○○温泉
   19:30 ○○ホテル
   ```

5. プランの各項目はDBレコードへの参照として保持し、施設名・料金は表示時にDBから取得すること
6. AI出力に候補外の参照が含まれる場合、システムはその項目を破棄すること
7. 日帰り指定の場合、宿泊を含めないこと
8. プランの中心が選択したサウナであることが視覚的に明確であること
9. 生成中の表示にAIや生成への言及を含めないこと
10. プランを保存できること

---

## 要件13: 行きたい

**ユーザーストーリー:** 気になるサウナを見つけたユーザーとして、後で見返せるよう保存したい。

### 受入基準

1. サウナ詳細および検索結果から「行きたい」に保存できること
2. ゲスト状態で保存を試みたとき、システムは認証を求めること
3. 認証完了後、システムは中断した保存操作を完了させること
4. 「行きたい」画面に、保存済みサウナの一覧を表示すること
5. 保存を解除できること
6. 将来的に地域ごとの整理が可能なデータ構造とすること
7. 保存が0件のとき、次の行動を1つだけ示す空状態を表示すること

---

## 要件14: 保存プラン

**ユーザーストーリー:** 生成したプランを気に入ったユーザーとして、保存して後から開きたい。

### 受入基準

1. 生成された休日プランを保存できること
2. 保存プランは日付・タイトル・プラン項目を保持すること
3. 「プラン」画面に保存済みプランの一覧を表示すること
4. 一覧から個別のプランを開けること
5. プランを削除できること
6. 保存プランを開いたとき、施設情報は保存時点のテキストではなくDBから取得した現在の情報を表示すること
7. 参照先の施設がDBから失われている場合、その項目を「情報が取得できません」と表示し、推測で補完しないこと

---

## 要件15: 認証

**ユーザーストーリー:** 保存したいユーザーとして、最小の手間でアカウントを作りたい。

### 受入基準

1. 認証画面の見出しは「行きたいを保存しよう」とすること
2. 認証手段は **Apple で続ける** と **Google で続ける** の2つのみとすること
3. **メールアドレス・パスワード入力をMVPでは提供しないこと**
4. Supabase Auth を使用すること
5. 認証前に端末側へ保存していた検索条件・直近閲覧を、認証後にユーザーアカウントへ移行すること
6. 認証を中断してもゲストとして検索・閲覧を継続できること
7. 検索・閲覧・詳細表示・プラン生成では認証を要求しないこと

---

## 要件16: 下部ナビゲーション

**ユーザーストーリー:** アプリを使うユーザーとして、迷わず主要画面に移動したい。

### 受入基準

1. 下部ナビゲーションは **探す / 行きたい / プラン** の3項目のみとすること
2. 4項目以上に増やさないこと
3. 現在位置を色以外の手がかりでも示すこと
4. 各項目のタップ領域は最低 44×44px を確保すること
5. アイコンに絵文字を使用しないこと

---

## 要件17: 予約

**ユーザーストーリー:** 行く施設を決めたユーザーとして、予約手続きに進みたい。

### 受入基準

1. **MVPでは予約機能そのものを実装しないこと**
2. 各施設の公式予約ページへ遷移する手段を提供すること
3. 予約URLはDBに保持すること
4. 予約URLが不明な施設では、遷移手段を表示せず、推測したURLを生成しないこと
5. 外部遷移であることをユーザーに分かる形で示すこと

---

## 要件18: データの正確性

**ユーザーストーリー:** 休日の計画を立てるユーザーとして、表示される情報が正しいと信頼したい。

### 受入基準

1. 施設情報はDBを Single Source of Truth とすること
2. **IMPORTANT:** 営業時間・料金・施設設備・クールダウン・予約情報等の事実情報を、AIが補完・推測してはならないこと
3. 不明な事実情報は「不明」と表示すること
4. 不明な値をDBに 0 や空文字で埋めないこと
5. AIの出力をそのまま事実情報として表示しないこと

---

## 要件19: デザイン規範

**ユーザーストーリー:** UIを見たユーザーとして、AIアプリではなく上質なアウトドアブランドだと感じたい。

### 受入基準

1. 絵文字をアイコンとして使用しないこと。統一された線画アイコンセットを使用すること
2. 過剰なグラデーションを使用しないこと
3. AIっぽいキラキラした演出を使用しないこと
4. 大量のカードで画面を埋めないこと
5. 過剰な丸角を使用しないこと
6. 説明文だらけの画面を作らないこと
7. モノトーンをベースに、自然を感じるアクセントカラーを用いること
8. 写真を主役とし、余白を確保すること
9. 各画面で情報の優先順位が明確であること
10. テキストのコントラスト比を 4.5:1 以上とすること

---

## 要件20: モックデータ

**ユーザーストーリー:** 開発者として、検索が正しく機能することを実データなしで確認したい。

### 受入基準

1. 実在施設を模したモックデータを **20施設以上** 用意すること
2. **対象エリアは関東（東京 / 神奈川 / 埼玉 / 千葉 / 茨城 / 栃木 / 群馬）に限定すること。** 関東以外の施設を含めないこと
3. 関東1都6県の中で地域を分散させること。特定の県に偏らせないこと
4. 都心から近い施設（1時間以内）と遠い施設（3時間前後）の両方を含め、移動時間による絞り込みを検証できること
5. 各施設は自然環境・クールダウン・サウナタイプ・料金・距離・貸切・体験がそれぞれ異なること
6. 検索条件を変更したとき、結果が変化することを確認できる構成とすること
7. 一部の施設は事実情報に意図的な欠損（NULL）を含み、「不明」表示を検証できること
8. 実在の施設名・電話番号・URLをそのまま使用しないこと
9. サ飯・観光・宿泊の紐付けデータも併せて用意すること
10. 出発地マスタも関東の主要駅・都市（東京 / 横浜 / 大宮 / 千葉 / 立川）に限定すること

---

- メールアドレス・パスワード認証
- レビュー・口コミの投稿と表示
- 地図上での検索・表示
- プランの共有・公開
- 施設側の管理画面
- 通知
- 多言語対応
